### Core Architecture Rules
1. **Decoupled Client-Server:** Streamlit and FastAPI run as two separate OS processes. The frontend does not import any backend code—all communication is stateless REST over HTTP.
2. **Dynamic Computation:** Endpoints compute numbers on demand (e.g., filtering 75,000 rows, fitting Prophet on the filtered slice). Nothing is hardcoded or mocked.
3. **Graceful Fallback:** The forecasting engine attempts Facebook Prophet first; if C++/Stan binaries fail, it automatically switches to `statsmodels` SARIMA without breaking the API.

## 2. Deep Logical Understanding (Under the Hood)

### A. Synthetic Data Design (`data_generator.py`)
- **Distribution:** Real e-commerce orders are **right-skewed** (many \$20–\$60 orders, rare \$500+ bulk orders). Using uniform or normal distributions looks fake; this project uses a **Gamma distribution** (`shape=4`, `scale=avg/4`).
- **Trend:** A 20% growth factor is applied linearly across the 2-year timeline (`trend = 1.0 + 0.20 * (day_idx / total_days)`).
- **Weekly Seasonality:** Weekends suffer an artificial 30% dip (`week_factor = 0.70`), reflecting typical B2B/online purchasing rhythms.
- **Holiday Spike:** November & December receive a `2.0x` multiplier to mimic Black Friday, Cyber Monday, and Christmas surges.

### B. Aggregation & Slicing (`data_loader.py`)
- The raw data is order-level. The forecaster requires a continuous daily series (`ds` and `y`).
- The loader uses Pandas `resample('D')` (or 'W' / 'ME') and aggregates revenue with `sum()`. Missing dates are filled so the time-series model doesn't see broken calendar intervals.

### C. Forecasting Mechanics (`forecaster.py`)
- **Prophet's Additive Model:**
  $$\text{Revenue}(t) = \text{Trend}(t) + \text{Weekly}(t) + \text{Yearly}(t) + \epsilon_t$$
  Prophet models trends using piecewise linear curves and seasonality using Fourier series.
- **Why Confidence Intervals Widen:**
  The 80% credible interval (`yhat_lower`, `yhat_upper`) is generated by sampling trend changes and noise into the future. Because errors compound day over day, day 1 has a narrow CI band, whereas day 60 or 90 has a wide band.
- **SARIMA Fallback:**
  Uses $\text{SARIMAX}(1,1,1)(1,1,0)_7$. Differencing ($d=1$) removes the linear upward trend to achieve stationarity, while $(1,1,0)_7$ captures the 7-day cyclical weekly rhythm.

## 3. Reverse-Engineered Interview Questions & Answers

### System Design & Architecture

**Q1: Why did you separate Streamlit and FastAPI into two services instead of running everything inside Streamlit?**
> *"Streamlit is great for UI, but it's single-threaded per user session and reruns the entire script on every user interaction. If we placed the Prophet model inside Streamlit, every UI click could lock the interface and duplicate heavy machine learning workloads. By placing the ML logic behind a FastAPI REST API, the backend can be scaled independently, cached, or reused across web, mobile, or third-party integrations."*

**Q2: What happens if 1,000 concurrent users request a 90-day forecast?**
> *"Right now, model training happens on-demand at request time. At 1,000 concurrent requests, CPU utilization would spike and requests would queue or time out. In production, I would solve this with:*
> 1. *An asynchronous worker queue (Celery + Redis) for model training.*
> 2. *A caching layer (Redis) storing forecast outputs keyed by `(category, region, horizon)` with a TTL.*
> 3. *Batch pre-computation: train nightly forecasts during off-peak hours and serve pre-computed projections instantly."*

**Q3: What is CORS, and why did you need it between Streamlit and FastAPI?**
> *"CORS (Cross-Origin Resource Sharing) is a browser security mechanism that blocks web pages hosted on one origin (port 8501) from fetching resources from a different origin (port 8001). We added `CORSMiddleware` in FastAPI with allowed origins so the Streamlit frontend can communicate with the backend seamlessly."*

### Machine Learning & Forecasting

**Q4: In layman's terms, what does an 80% confidence interval mean on your chart?**
> *"It means the model expects 80 out of 100 actual future revenue values to fall within the shaded band. It gives executives a best-case and worst-case corridor for inventory planning, rather than giving a single misleading point prediction."*

**Q5: Why did you pick Facebook Prophet over Deep Learning (like LSTM or Transformer)?**
> *"Three reasons:*
> 1. *Data size: We have 2 years of daily data (~730 points). Deep learning models require tens of thousands of data points to avoid severe overfitting.*
> 2. *Interpretability: Prophet decomposes revenue into readable components (growth trend, weekly cycle, holiday spike). Business stakeholders can understand why the prediction is moving.*
> 3. *Speed and robustness: Prophet handles outliers and missing dates without manual imputation."*

**Q6: Why is SARIMAX your fallback, and what does the `(1,1,1)(1,1,0)[7]` order mean?**
> *"If Prophet fails to compile on an operating system without C++ tools, SARIMAX from `statsmodels` runs on pure Python/C wheels. The order means:*
> - `(1,1,1)`: One autoregressive term (yesterday's revenue), one differencing step (to flatten the upward trend), and one moving-average term (smoothing residual shock).
> - `(1,1,0)[7]`: A seasonal component with a 7-day period to capture weekly cycles."*

### Data Engineering & Edge Cases

**Q7: How does your backend handle edge cases like invalid date ranges or empty filters?**
> *"We return standard HTTP status codes instead of letting Python crash:*
> - *If `start_date > end_date`: returns `400 Bad Request`.*
> - *If a filter combination yields zero records: returns `404 Not Found` with a message asking the user to broaden filters.*
> - *If a slice has fewer than 14 days of data: returns `422 Unprocessable Entity` because 14 days is the minimum needed to detect weekly seasonality."*

**Q8: Why did you use Gamma distributions to generate order revenues?**
> *"Because real consumer spending is asymmetrical. Most buyers spend a moderate amount, while a small fraction spend significantly larger amounts. A standard Gaussian bell curve would produce negative revenues or an unrealistic symmetry, whereas a Gamma distribution naturally creates the positive-only, long-tail distribution observed in e-commerce."*

### Production Readiness

**Q9: How would you transition this prototype into enterprise production?**
> 1. *Storage: Migrate `sales_data.csv` to PostgreSQL / BigQuery with indexed partitions on `order_date`.*
> 2. *Containerization: Write a `docker-compose.yml` defining isolated containers for FastAPI, Streamlit, and Redis.*
> 3. *Monitoring: Implement Prometheus metrics on FastAPI for latency tracking and model drift monitoring (comparing predictions against actual sales as days elapse).*
> 4. *CI/CD: Automated pytest suites testing endpoint contracts against Pydantic models before deployment.*
